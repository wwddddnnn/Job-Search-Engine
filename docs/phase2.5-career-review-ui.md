## 目标与范围

用户在项目配置好的 Python 3.12 Conda 环境中运行启动命令，在浏览器打开本地应用，亲自导入、整理、编辑、核验并发布职业档案。交付必须可实际操作和人工验收。

首版支持多份 `.md` 简历。用户以手工整理为默认方式，将不同简历中的经历汇总到同一份个人职业档案。职业档案应容纳全部经历，供后续按目标职位生成不同简历；本阶段不实现简历生成。

本阶段包含：本地 Web UI 与必要的 HTTP/application service 契约、审核草稿持久化、自动保存、部分发布、多套 LLM API 配置、带引用的优化/合并操作入口，以及明确标识的 Mock 调用与结果应用。

本阶段不要求完成 PDF/DOC/DOCX 导入、真实 LLM 网络调用、自动简历抽取、Matching、Application、Agent/MCP。真实 LLM 调用仍属于后续 B 步；不能把“配置入口可用”表述为“真实调用已接入”。

## 页面与基本流程

1. 启动本地应用，选择中文或英文界面。简历和用户内容保留原始语言，不因切换界面语言而自动翻译。
2. 导入 `.md` 简历，可切换查看多份已导入文档。
3. 左侧默认显示排版后的 Markdown，并可切换源码；右侧编辑经历、成果和技能。
4. 鼠标选中原文后，可“新建经历”“添加成果”“添加技能”；也可以不选原文，直接手工填写。
5. 用户可以编辑、确认、拒绝或标记待澄清。确认经历不自动确认所有成果和技能。
6. 整理内容与核验进度自动保存，关闭页面或重启后可继续。
7. “发布档案”是单独的明确确认操作，发布前展示本次内容与变更摘要。
8. 发布后可查看职业档案及历史版本，并继续整理剩余草稿。

界面不提供“关联为证据”按钮，不要求用户手工维护证据关系。用户觉得描述不合适时，直接修改内容。

## 草稿、来源与版本

- 编辑内容独立保存为审核草稿，不能覆盖原始 Markdown 或历史抽取输出。手工整理不依赖成功的 LLM 抽取运行。
- 从原文创建条目时，后台自动保留文档引用和原文位置；修改时保留原文及修改记录。来源引用用于追溯，不等于修改后的表述已经被原文支持。
- 无文档依据的新增事实，在用户明确确认后以 `user_assertion` 保存，不伪装成简历事实。证据链仍由后端维护，不增加手工关联步骤。
- 删除整理中的条目支持撤销；删除已发布条目只影响下一版，历史版本仍保留。发布摘要需明确列出删除。
- 支持部分发布：只发布用户明确确认的新增或修改，其余内容继续保留在草稿。已有且未修改的已发布经历默认保留。
- 对已有条目的未确认修改，不应在部分发布时导致旧版已确认事实消失。用户明确确认删除后，才在新版本移除。
- 自动保存、Mock/LLM 输出、一键替换和自动合并均不自动将事实设为 verified。修改已确认内容后，需要重新确认修改后的内容。
- 发布应基于明确的档案基础版本，检查版本冲突，避免旧页面覆盖后来发布的内容。
- 没有已发布档案时展示可继续操作的空状态，不能将其混同于数据损坏；合法空档案与基础设施错误应有不同界面文案。

## 多份简历与重复经历

多份简历共同补充一份职业档案。导入新简历不会覆盖已有经历。

默认由用户选择新建经历，或将新内容添加到已有经历，再选择补充或替换字段；不自动合并重复经历。

用户也可显式选择“LLM 协助合并”，指定参与合并的内容。调用完成且输出通过校验后，自动将合并结果写入编辑草稿，不再要求逐字段采纳；保留合并前内容并支持撤销。合并不修改原始简历或历史档案，发布仍需单独确认。

Phase 2.5 用 Mock 接口演练合并流程；真实 LLM 合并由 B 步接入。输出无效、调用失败或目标草稿在等待期间已修改时，不得静默覆盖现有编辑。

## 自动保存与撤销

自动保存覆盖整理内容、审核决定、LLM 引用、用户 prompt 和配置选择；重启后能够恢复。

界面至少区分“未保存/待保存”“保存中”“已保存”“保存失败”，已保存只能在后端确认持久化成功后显示。失败时保留当前输入，并允许重试。防止旧保存请求覆盖新编辑。

发布必须使用已保存且与用户当前所见一致的草稿版本。撤销删除、替换或合并时，恢复相应编辑内容并继续自动保存；不能删除历史发布记录或修改原始输入。

## LLM API 配置

用户可添加、修改、删除多套配置，并在优化/合并面板中切换。首版按 OpenAI 兼容接口设计，其他接口后续扩展。

每套配置包含：名称、API 地址、API Key、模型名。

- API Key 保存在本机，应用重启后可继续使用；已保存的 Key 在界面中只显示掩码。
- Key 通过后端受控的本地秘密存储管理，不放入浏览器持久化存储、普通日志、审计正文或 Mock fixture。具体存储实现需在编码设计时明确；显示掩码不等于存储加密。
- 修改普通字段不应误把掩码当成新 Key；删除配置时同时处理其保存的凭据。
- 读取配置仅返回非秘密字段及是否已设置 Key 等状态。审计记录配置变更动作，不记录 Key 内容。
- 本阶段配置保存不触发真实请求，也不声称已经验证连通性。

## 带引用的优化交互

用户可从左侧简历原文、右侧编辑字段中用鼠标选取一句或一段文字，也可引用整个经历/成果。

选择“用 LLM 优化”后，侧栏显示引用内容及其来源，用户填写自己的 prompt 并选择 API 配置。请求上下文应保留选区/条目的稳定标识及版本，以确定结果应应用到哪里。

结果区分别展示优化建议和改写结果。优化结果由用户点击“一键替换”后应用：

- 引用右侧字段选区：替换原选区；引用整条经历/成果：应用到对应条目。
- 引用左侧原文：用户选择右侧目标字段或新建条目，原始 Markdown 不变。
- 保存替换前内容，支持撤销；替换只影响编辑草稿，不直接发布。
- 结果返回前目标已变化时，应提示用户重新选择/核对目标，不能按过期位置覆盖新内容。

这与“LLM 协助合并”不同：优化需要点击采纳，合并在用户显式启动后自动应用到草稿；两者均可撤销且仍需发布确认。

## Mock 与真实调用边界

普通模式提供引用、prompt、配置和操作入口；真实生成能力明确显示“待接入”，不得静默返回假建议。

提供独立、明确标识的 Mock 模式，通过假接口响应检查加载、结果展示、一键替换、自动合并、撤销和错误状态。Mock 不需要真实 API Key，不发外部请求，建议和结果始终标明演练来源。

后续 B 步用真实 provider 实现替换 Mock 调用能力，继续复用引用、prompt、结果展示、应用草稿及确认发布契约。

## 技术选型与后续迁移（已确认）

Phase 2.5 采用 Python 标准库本地服务与原生 HTML/CSS/JavaScript，先完成人工操作闭环，再根据实际维护需要决定是否迁移 Vue。

- **本地服务**：使用 `http.server.ThreadingHTTPServer` 提供静态资源和 `/api/...` JSON 接口，运行在项目既有 Python 3.12 Conda 环境中。只绑定 `127.0.0.1`，限制静态资源访问路径并校验写请求来源（机制见下条）；该入口用于本地单用户应用。
- **写请求来源校验**：只查 `Origin` 不足以防护（同源策略不阻止跨站"发"请求；DNS rebinding 下 `Origin` 也可能看似合法）。启动时生成随机 token 注入页面，写请求必须带 `X-JSA-Token`；同时校验 `Host` 为 `127.0.0.1[:port]`（挡 rebinding）。只读 GET 不强制 token。
- **HTTP 契约**：`/api/...` 只返回 JSON，不返回 HTML 片段；`ApplicationError` 映射到状态码（`ValidationError` 422 / `NotFoundError` 404 / `ConflictError` 409 / `InvalidStateError` 409 / `InfrastructureError` 500），错误体统一 `{error: {code, message, correlation_id}}`。**前端按 `code` 做中英文文案，不解析 `message` 文本**。`preview_publication` 增加可选 `context` 参数，使只读预览的错误也带 `correlation_id`（保持无 context 时的现有行为）。
- **前端资源**：HTML、CSS、JavaScript 和其他页面资源全部随项目本地提供，不引入前端框架、不连接 CDN，不要求安装 Node.js 或前端构建工具。
- **启动体验**：通过一个 Python 启动命令提供页面和 API，用户在浏览器中操作。
- **模块划分**：使用原生 JavaScript 模块，将 API 请求、编辑状态、编辑操作（替换/合并/删除/撤销）与 DOM 渲染分开；文档查看、经历编辑、LLM 面板和配置管理分模块组织，避免集中到一个大脚本。**DOM 只允许出现在 view 模块**，其余模块不得直接读写 DOM——这样将来迁 Vue 只需替换 view 模块，其余模块原样复用。
- **目录落点**：HTTP 入口与 adapter 放 `src/job_search_assistant/adapters/web/`，页面资源放其下 `static/`；`applications/`、`matching/` 仍是后续阶段占位，不放业务逻辑。
- **界面偏好持久化**：界面语言等偏好存服务端（新增迁移里的一张设置表），重启后保持；浏览器本地存储不用于业务状态。
- **业务边界**：保存、确认、发布、版本冲突和审计由 Python 应用服务负责。前端通过 JSON API 读取和提交数据，不依赖后端生成的 HTML 片段；API 不暴露数据库内部结构。
- **编辑稳定性**：局部更新界面，避免重建整个表单导致光标或选区丢失。自动保存请求及结果应用携带稳定条目标识和版本，防止过期请求覆盖新内容。
- **Markdown 范围**：标准库没有内置 Markdown 解析器，首版自行实现并明确说明常用子集（标题、段落、列表、强调、链接、代码块），不承诺完整 CommonMark 兼容。源码视图保留完整原文；渲染时转义内容、不执行原始 HTML，并限制链接协议。

后续若组件复用、页面数量或状态同步的维护负担明显增加，可迁移到 Vue。迁移重点是页面渲染和事件绑定；数据库、Python 应用服务及已定义的 JSON API 应尽量复用。原生前端代码并非全部可以直接迁移，需要预留界面重写成本。

Vue 与后端 HTTP 框架独立选择，采用 Vue 不强制要求同时改为 FastAPI。未来若引入 Vue，其开发/构建使用 Node.js 和项目级 npm 依赖，与 Python Conda 环境分别管理；本阶段不创建或安装这套前端工具环境。

## 实现边界与建议切片

沿用应用服务为统一入口的规则：UI/HTTP adapter 不直连数据库，也不直接调用 store 内部写接口。所有写操作携带 actor、correlation ID 和幂等键；业务变更、审计和幂等完成状态保持一致。数据库变更新增迁移，不修改已应用迁移。

Phase 2 的确认接口仅支持抽取结果索引勾选；本阶段需要增加或扩展手工审核草稿、编辑、删除、部分发布及版本冲突的契约，不能让 UI 依赖现有 store 绕过这些服务。后台继续满足未确认事实不进入已发布档案/VerifiedEvidencePack 的约束。

延续现有零第三方运行时依赖约定，按上述已确认的 stdlib 与原生前端方案实现。Markdown 渲染和源码视图须按不可信文档处理，不执行文档携带的脚本。

## 验收标准

1. README 提供实际可执行的单个 Python 启动命令、本地访问地址和停止方法；使用项目既有 Conda 环境，不要求用户自行装配服务对象、安装 Node.js 或执行前端构建。页面资源全部本地提供，不连接 CDN。
2. 用户可切换中英文界面，简历原文语言不变。
3. 可导入多份 `.md`，查看渲染/源码，选中文字创建条目，或直接手工添加；没有“关联为证据”操作。
4. 经历、成果、技能可编辑、核验和删除；整理与核验进度自动保存，保存状态准确，刷新/重启后恢复。
5. 部分发布生成新版本，保留未修改的旧事实及尚未发布的草稿；删除/修改不改变历史版本。
6. 手工补充和修改具备后台来源/修订记录，未确认内容不进入可信事实包。
7. 可新增、修改、删除多套 API 配置并切换；Key 本地保存、重启可用、界面掩码，日志与读取响应不泄露 Key。
8. Mock 模式支持选区/整条引用、自定义 prompt、建议与改写结果、一键替换及撤销；普通模式明确说明真实调用未接入。
9. 用户可手工处理重复经历；显式启动 Mock 合并会自动写入草稿，可撤销，仍需人工发布。
10. 测试覆盖自动保存顺序/失败、幂等重试、版本冲突、部分发布、旧结果覆盖防护及历史保留。自动测试不访问外部网络；本地 HTTP/浏览器验证可使用本机服务。HTTP adapter 用标准库 `ThreadingHTTPServer(("127.0.0.1", 0))` 起真实端口 + `urllib.request` 测试（不引入第三方客户端），至少覆盖：错误码映射、缺少/错误的 `X-JSA-Token`、错误的 `Host`、路径穿越、非法 JSON 与超限请求体、未知字段。
11. 提供独立演练数据与人工验收步骤，演练数据不冒充用户已确认的职业事实；本阶段不要求 PDF/DOC 或真实 LLM 调用通过验收。

## S1 与 S2a 契约（已交付并通过审查）

下文说明 S1 审核服务；S2a 启动入口、人工验收与 HTTP 契约见 [README 第 4 节](../README.md#4-本地启动s2a--s2b)。

装配：`CareerReviewService(store=SQLiteReviewStore(foundation.database))`。
公开类型由 `career` 导出；应用服务和 SQLite 实现分别由 `app_services` 与
`infrastructure.sqlite` 导出。使用方式见 `tests/test_career_review.py`。

- `create_draft(profile_id, display_name?, context, idempotency_key)`：每个 profile
  一份持久化审核草稿；已有档案从当前版本建立可编辑条目，没有档案时以 display_name 创建
  未发布的 profile，不需要文档或抽取运行。同 profile 再打开返回已有草稿。
- `get_draft(draft_id)`：从数据库读回条目、来源、核验状态、软删除标记和草稿版本。
- `create_item` / `edit_item` / `delete_item` / `restore_item`：创建、修改、软删除和撤销删除。
  子项通过稳定的 `parent_id` 归属经历。编辑和撤销删除后必须重新确认。
- `decide_item(decision=confirm|reject|clarify|confirm_delete)`：只核验指定条目；
  已确认且之后未修改的条目重复 `confirm` 不改变条目内容、确认时间或 dirty 状态，
  不额外产生发布变更；已发布且未修改的条目不进入发布摘要、不因此产生新档案版本。
  首次确认后尚未发布的变更仍保留；命令仍按既有保存规则递增草稿版本并记录审计。
  编辑后仍必须重新确认，才能进入发布摘要。
  `confirm_delete` 仅适用于已软删除条目，普通 `confirm` 不能确认删除。
- 所有条目写操作携带 `draft_id`、`expected_version`、`context`、`idempotency_key`。
  返回的 `ReviewDraft.version` 是本次已持久化版本；旧版本保存返回 `ConflictError`。
- `preview_publication(draft_id, expected_version, base_version_id)` 为只读预览，
  返回新增、修改、删除清单；无可发布变更时三个列表均为空，不抛异常。
  即使摘要为空，expected_version 仍须匹配已保存草稿版本，base_version_id 仍须同时
  匹配草稿基础版本和当前档案版本，
  不一致返回 `ConflictError`。空变更的 `publish` 仍返回 `ValidationError`，不生成版本。
  `publish` 使用同一组版本参数并携带 context / 幂等键，
  在事务内重新检查版本，返回新档案版本、草稿快照和实际发布摘要。

`base_version_id=None` 明确表示此前没有发布版本。发布后草稿版本也递增，未确认编辑保留，
它们的已发布事实引用推进到新版本的旧表述副本。新的已确认子项若父经历尚未发布，则继续
等待；已有事实不会因未确认编辑、拒绝、待澄清或尚未确认的软删除而消失。
确认删除整段经历表示移除该经历及其已发布子项，预览和发布摘要逐项列出这些删除；
子项从新发布版本移除，编辑内容仍保留在审核草稿中，`published_id` 置空。
撤销父经历删除后可以继续整理并逐项确认。

来源使用 `ReviewSource(document_id, DraftEvidence(...))`，新建来源必须含
`source_locator`（S2b 使用 `codepoint:9:26`，以不可变文档文本的 Unicode 码点为坐标，
从 0 起、左闭右开；不使用含糊的 `offset` 前缀）；已有 Phase 2
档案的 excerpt-only 引用也会保留。待发布引用以内嵌引用值保存于草稿，不建立平行证据表。
确认发布后沿用 `ExperienceEvidence`，无文档依据的事实使用 `user_assertion`。
0005 为现有 evidence 增加可选 `experience_skill_id`，使手工技能自己的来源与父经历来源
可区分；旧 Phase 2 数据继续支持原有经历级证据回退。
`experience_skill_id` 当前仅表示技能级证据归属，手工技能不借用父经历来源，
不承担更细粒度 claim→evidence 语义；Phase 3/4 如有此需求，须另行设计并新增迁移。

草稿的已发布引用缺失或类型不一致返回 `ConflictError(code=conflict)`；版本事实内部
技能或父经历引用损坏返回 `InfrastructureError(code=infrastructure_error)`，不泄漏
`KeyError` / `StopIteration`。

`SQLiteReviewStore` 对 `SQLiteCareerStore` 私有加载/写入方法的复用属于同层内部契约，
CareerStore 内部重构须同步审阅 adapter；这不是 UI/HTTP 可调用的公开接口。
`tx.get_facts` 借助 WAL 从独立读连接读取已提交、不可变的版本事实，外层事务持有写锁并
检查当前版本指针。该路径只读、不得写入、不得依赖未提交数据。

保存结果只在事务提交后返回；事务包含业务变更、`career.review.*` 审计与幂等完成记录。
失败全部回滚，相同输入与幂等键可重试。已完成请求重试返回原始响应（包括原草稿版本），
不会重新执行，也不会覆盖之后的编辑。未来 adapter 必须保留失败输入、串行提交或处理版本
冲突，并忽略比当前视图更旧的响应；有待保存输入时不得发布，须先取得该输入的保存确认，
再将该版本用于预览和发布。

`GetCareerProfileSnapshot` 对未发布 profile 返回 `profile_version_id=None, version=0`、
空经历列表；已发布的合法空版本返回实际版本 ID / 版本号和空列表。不存在的 profile
仍为 `NotFoundError`，存储错误不转成空状态。`GetVerifiedEvidencePack` 继续拒绝无可信事实
的档案，且不会读取审核草稿。


## S2b 契约（已交付，本轮审查通过后提交）

人工验收、启动方式见 [README 第 4 节](../README.md#4-本地启动s2a--s2b)。
S2b 不包括 S3/S4 的 LLM 配置、Mock 优化或合并。

- `GET /api/profile/versions`：`{id, version, created_at}` 列表，按版本倒序；无版本返回 `[]`。
- `GET /api/profile/versions/<id>`：指定不可变档案快照。history 选择只改变展示的 snapshot，
  不替换当前 profile、不写草稿或档案。
- `POST /api/review/<action>`：共有 `draft_id`、`expected_version`；除 preview 外均要求
  `idempotency_key`。HTTP 生成 context（actor、correlation ID），由应用服务执行事务。
  顶层非对象、未知/缺失字段返回 `ValidationError` / 422；非法 JSON 为 400。
- create：`kind`、`fields`，可选 `parent_id`、`selection`；edit：`item_id`、`changes`；
  decide：`item_id`、`decision=confirm|reject|clarify|confirm_delete`；delete/restore：
  `item_id`。以上返回已保存草稿（含 version、items、sources 和状态）。
- selection：`{document_id, start, end}`，以 GET document 返回的完整原文为基准，
  Unicode 码点、0 起、左闭右开。reader 将 DOM UTF-16 下标转换为码点；后端校验范围并
  生成 `source_locator="codepoint:start:end"` 与原文摘录，保留 CRLF、emoji 等原始内容。
- preview：接受 `base_version_id`，公开返回 `{draft_id, draft_version, base_version_id,
  summary, content}`。**`content` 是新增公开字段**，为 `{kind, fields}` 列表，表示本次
  实际发布的全部内容（含保留的旧事实），不是仅有变更摘要；summary 的 added/modified/deleted
  列表描述本次变更。preview 只读，空变更可预览，空变更不能 publish。
- publish：同样接受 `base_version_id`，返回 `{draft, profile_version_id, version, summary}`。
  重新检查已保存草稿与档案基础版本。失败重试保持原 publication 请求及同一幂等键，
  取消预览或开始新编辑才废弃该请求；有未保存输入/composer 时 editor-actions 阻止预览和发布。
- 修改已确认内容立即显示待核验，保存后仍须重新确认；reject/clarify 不使新事实进入发布内容。
  无已发布档案、尚无草稿、草稿无条目分别展示未发布提示、创建草稿提示和手工填写引导。

### 冲突恢复取舍：选择 B

采用成本较低且可测试的「复制后刷新」：冲突不自动合并、不自动改 expected_version 重发。
失败 composer 保留全部字段，使用 readonly 而非 disabled，允许聚焦选中复制；已有条目编辑
也保留未保存文字。冲突隐藏原样重试按钮，中英文指引均要求先复制所有未保存字段，再刷新
读取最新草稿，对照后重新粘贴、保存、确认与发布。新页面产生新的幂等键并使用最新草稿版本。
普通网络失败仍原样重试。没有静默丢弃队列；刷新是用户在复制后的显式操作，未复制文字不会
跨刷新自动恢复。此方案避免引入 A 所需的额外重载、冲突合并和队列变基状态。

JS 测试通过全新 JavaScriptCore 上下文模拟刷新，验证冲突输入可复制、最新版本重新保存成功
并解除预览门控；HTTP 测试验证冲突、GET 最新草稿、新键保存及发布完整链路。
逻辑测试依赖 **macOS 系统 JavaScriptCore，非 darwin 平台会静默 skip**（unittest 显示 skipped）。
view 测试只用最小 DOM 夹具验证事件与渲染分支，不代表真实浏览器验收；双向选区、输入法组合
输入、粘贴大段文本必须按 README 人工操作，不能声称已被自动测试覆盖。
